# 大众向选片与“绷”弹幕加权

主流程默认面向第一次刷到视频、不了解主播的普通观众。初选、边界与看点复核、标题生成、封面文案审校共用这个方向：不要求先认识成员、粉丝昵称、CP关系或过往直播；一段即使去掉人物名字，仍应能说清楚发生了什么、哪里意外或为什么值得看。

互相表白、熟悉开场白、撒娇、生日祝福等不因粉丝喜欢就自动入选。有片内独立成立的反差或故事仍可考虑，不是一律排除某类题材。事件、引文、完整性、时长及默认85分门槛照常校验，允许零条。提示词只能约束模型判断，不能保证大众一定喜欢；目前仍需要人工回看。

## 输入独立弹幕

支持 UTF-8 ASS 的 `[Events]` / `Dialogue`，以及B站/常见录播器的 XML `<d p="秒数,模式,字号,颜色,发送时间,池,用户标识,消息ID">文字</d>`。XML第一个字段必须是相对于录播的秒数，不是Unix时间。

只有已经烧录弹幕的MP4时，本功能不会自动读到“绷”。当前没有接入视频OCR。语音字幕SRT、主播说“绷不住了”、文件名写“弹幕版”都不作为弹幕数据。必须使用对应这段录播的独立弹幕文件；不扫描旧输出中的字幕ASS。

在**原完整启动命令**后追加：

```bat
--danmaku "E:\recordings\sample.xml" --analyze-only
```

`--danmaku` 的路径按命令执行位置解析。也可在本机JSON配置中新增顶层段，配置路径按项目根目录解析：

```json
"danmaku": {
  "path": "",
  "offset_seconds": 0,
  "lookback_seconds": 8,
  "tail_seconds": 2,
  "max_priority_bonus": 5
}
```

将 `path` 填为实际 XML/ASS 路径。留空则不加权，原来的只用字幕流程仍可运行。路径不存在、格式错误或全部弹幕都超出录播范围时会报错，不会假装读取成功。

两种输入走同一主流程：**只有视频 → 本地转写 → 选片**；**视频 + 弹幕 → 本地转写 + 观众语境/反应 → 选片**。如果原配置留有上一场弹幕路径，本次没有弹幕时可追加 `--danmaku ""` 明确清空。普通入口不会扫描目录中的 ASS，避免误读成语音字幕。

[录播姬自动入口](recorder-integration.md) 则会查找原视频同名 XML：默认 `danmaku_policy=optional`，等待后仍缺失就只处理视频；可设为 `required` 强制等待。已经存在但无效的 XML 仍需检查，不会自动跳过错误。

同样的 `--danmaku` 可与 `--prepare-only` 一起使用，在本地转写后先导出 `danmaku.signals.json` 检查时间，不调用选片API。`--check` 只检查文件存在和扩展名，不证明弹幕与画面已同步。`--danmaku` 不能搭配仅改字幕、仅打包或 `--restyle`，这些模式不会重新选片。

## 时间对齐

`视频时间 = 弹幕文件时间 + offset_seconds`。例如弹幕文件中的10秒实际对应视频中的13秒，填 `3`；长录播截取后的弹幕时间仍从整场起算时，可能需要负值。应先在几处核对相同弹幕与画面，不能靠文件名认定同步。程序只能检查时间数值是否有效，不能自动证明选择了正确场次。

反应往往晚于触发：默认提示模型回看“绷”出现前8秒及后2秒的内容。该范围只用于查找，不作为切片起止；最终仍按提问、铺垫、转折及收尾选择字幕ID。

## 如何增加权重

1. 含“绷”的弹幕每条记一次，“绷绷绷”不算三票。“绷带、紧绷、绷紧”等普通词不作为该反应。
2. XML有消息ID时去除重复记录；有用户标识时，同一用户在同一10秒桶内最多计一次。ASS一般没有用户标识，只能去除时间与文本完全相同的记录，不能据此声称独立观众数量。
3. 给初选和边界复核传入实际时间、计数及建议回看范围，并提供有限的观众评论抽样作为语境。评论明确标注为不可信观众数据，禁止执行其中的指令，不把弹幕文本冒充主播说的话。
4. 初选分和复核分**各自达到85**后，才参与加权排序。`score = min(selection_score, quality_review.score)` 保持不变。
5. 候选附近每个10秒桶中，取最高的去重反应数作为加权依据：默认每条加1，最多加5。`priority_score = score + danmaku.bonus` 是排序值，不是新的内容分或准确率；长片不因跨过更多桶而累计无限加分。

例如两条已通过的片段，内容分分别88和85；后者附近有5条有效“绷”，排序值变为90，可以优先于88分片段。若后者内容分只有82，仍直接弃选，不能靠加5变成合格。刷屏和粉丝内梗也不证明大众会喜欢。

## 如何辅助理解

除“绷”的统计外，每个初选/边界复核窗口最多向模型提供 **24 条评论、每条最多 120 字**，按视频时间组织。同窗口相同文本只保留一条，超过数量时按时间均匀抽样，不发送用户 UID 或消息 ID。评论范围包含配置的反应延迟余量，不扩展模型可引用的语音字幕范围。

这些评论能提示观众在回应哪个问题、为何发笑、哪段语境值得核对；没有“绷”的普通弹幕同样可以进入语境。评论可能在开玩笑、误解或刷屏，不能据此确认发言人、画面动作或人物关系。最终证据仍必须来自对应字幕 ID 的真实原文；未接入视觉/OCR，也不声称抽样理解了全部弹幕。

这会增加少量输入 token。真实效果还需要录播回看验证，不能把功能接通或测试通过当成质量提升的统计证明。

## 结果与缓存

- `danmaku.signals.json`：输入文件指纹、时间偏移、有效/超范围消息数及各反应区间。文件路径和标识留在本机，不提交Git。
- 同文件还记录可用于语境的评论数量、窗口条数上限和解析策略版本；普通评论内容只作为有边界的模型输入，不替换原始 ASR。
- `analysis.json`：受众 `quality_policy.audience=general`；通过片段的 `danmaku` 与 `priority_score` 和原看点分分开保存。
- `report.html`：是否读取弹幕、加权和内容分；没有弹幕输入会明确显示未启用，而不是推测画面里没有“绷”。

提示词及弹幕语境策略改变后，重新选片会重新调用模型，已完成的ASR可复用。弹幕策略版本已更新为2；修改弹幕文件、时间偏移或回看范围也会使对应请求缓存失效。只改 `max_priority_bonus` 不重算模型分，可以复用有效响应并重新排序。旧报告和旧成片不会因修改代码自动变更，也不会被删除。

实现见 `core/danmaku_signals.py`、`core/highlight_selection.py` 和 `resources/prompts/`。旧版 `legacy/danmu/` 保持独立，不作为本功能的默认入口。
